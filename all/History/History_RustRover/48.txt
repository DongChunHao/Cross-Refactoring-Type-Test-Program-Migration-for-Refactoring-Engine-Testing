/* Refactoring Settings:
Refactoring Type: Pull Fields Into New Substruct (Feature Request)
Refactoring Target: Selected fields `x: i32, y: i32` inside `struct A`
Refactoring Scope: Generate new sub-struct, replace original fields with a single field of the new struct type, update all construction and access sites
Plugin Environment: IntelliJ Rust plugin
Macro expansion engine: new
Name resolution engine: new
Trigger Operation: Select multiple struct fields and invoke "Move fields into new substruct" intention/refactoring
*/
/* Feature request description:
Add a dedicated refactoring to take a subset of fields from a struct, extract them into a new named sub-struct, and replace those fields in the original struct with one field whose type is the new sub-struct.
This is especially useful in Rust for borrowing/subfield splitting: separating fields into distinct structs allows simultaneous mutable borrowing of different members, which is not possible when they are top-level fields of the same struct.

Before:
struct A {
    x: i32,
    y: i32,
    name: String,
    color: Color,
}

Desired after refactoring:
struct Point {
    x: i32,
    y: i32,
}

struct A {
    position: Point,
    name: String,
    color: Color,
}

Additional required rewrite logic:
1. Struct literals like `A { x: 1, y: 2, name: "hi".into(), color: red }` → `A { position: Point { x: 1, y: 2 }, name: "hi".into(), color: red }`
2. Field access `a.x` → `a.position.x`; `a.y` → `a.position.y`
3. Pattern matches: `let A { x, y, name, color } = a` → `let A { position: Point { x, y }, name, color } = a`
4. Handle visibility, derive attributes, docs, and generics: if original struct has generics, propagate them to the new substruct as needed.
5. Allow user input for: new substruct name (`Point`), new field name (`position`), visibility of the substruct and its fields.

Potential edge cases:
- Tuple structs
- Fields with attributes (`#[serde(rename)]`, etc.)
- Structs with `#[derive]` macros that expect flat fields
- Nested existing sub-structs
- Method `impl` blocks that access the extracted fields

Underlying motivation:
Rust’s borrow checker treats a struct as a single value; two mutable borrows of different top-level fields are permitted, but splitting into separate structs is a common way to organize state when you need to group related data and reason about borrow granularity. This refactor would automate the mechanical rewrite instead of requiring manual editing and fixing every usage site.
*/
// Before
struct A {
    x: i32,
    y: i32,
    name: String,
    color: Color,
}

// Desired after refactoring
struct Point {
    x: i32,
    y: i32,
}

struct A {
    position: Point,
    name: String,
    color: Color,
}
